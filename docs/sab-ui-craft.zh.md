# SAB UI Craft —— UI 品质评审与打磨

## 目的

让界面显得**克制、清晰、精确、完整**，而不只是被装饰过。

品质来自信息层级、排版、留白、层级关系、交互一致性，以及真实而完整的状态——而不是阴影、渐变、动画或玻璃效果的数量。

遵循 **small-and-beautiful（小而美）**：先聚焦核心任务，先统一和删除，最后再加细节。融合苹果式的专注、匠人级的细节和轻量的交互，但不模仿任何具体产品的视觉风格。

## 何时使用

- 用户说 UI"没有质感""太平""像后台管理页""像拼装起来的组件"，想要原因或修复方案。
- 用户提供截图、设计稿或现有前端代码，要求做 UI/UX 评审、打磨或 UI 重构。
- 用户想为颜色、字体、间距、圆角、状态、动效等建立或统一设计规则。
- 用户想把原型做成可交付的产品，而不是继续加功能。

**不适用：** 品牌识别、标志设计、营销插画、纯后端工作、纯逻辑或数据流缺陷修复、以动效为主要交付物的动画工作，或完整的无障碍审计。

**先确定模式：**
- **评审模式**：用户只提问、征求建议或方案。做分析并给出可执行的改动建议；未经要求不要改代码。
- **实现模式**：用户明确要求修改、实现或重构。先读项目，做最小的必要改动，并验证。
- **新建模式**：还没有现成 UI。先确认用户的关键任务和视觉约束，再做一个小的、完整的方案。原则上 v1 的核心功能不超过 3 个。

如果对话中途从评审转为实现，先复述前 3 项改动并确认范围，再开始编辑。不要把评审扩成重写。

## 前提条件

- 能拿到证据：截图、正在运行的页面，或相关源码。只有源码时，说明哪些视觉和交互判断无法验证。
- 实现模式下，有修改项目的权限，并能运行项目已有的检查。
- 计算对比度时用实际色值算比值；中文界面要确认字体栈能正常渲染实际用到的每个字符。

## 不可妥协的规则

1. **先证据，后结论。** 用截图、运行中的页面、代码和现有规则说话。没跑过、没看过的效果，不要声称已验证。
2. **保留产品身份。** 沿用现有品牌色、组件体系和平台惯例，不要把每个项目都变成同一种灰白风格。
3. **功能优先于装饰。** 绝不用可读性、键盘可达性、对比度、布局稳定性或性能去换"高级感"。
4. **先删除和统一。** 在考虑新增元素之前，先删掉重复入口、无意义分隔线、多余标签和占位式装饰。
5. **避免重写。** 复用项目已有的布局、设计 token、组件和图标；除非确有必要，不引入新的 UI 库或动画依赖。
6. **覆盖完整状态。** 不要只打磨默认截图的那一屏；加载、空、错误、禁用、悬停、聚焦、选中和窄屏状态都要覆盖。
7. **不做假交互。** 按钮、标签页、设置项和导航必须对应明确的行为；不要保留看起来能点、实际没反应的东西。

## 工作步骤

### 1. 获取 UI 上下文

在现有项目中，尽量了解：
- 目标用户、主要任务，以及页面最重要的内容和操作。
- 当前截图或运行中的页面；如果有多种尺寸，先看主桌面视图，再看更窄的视图。
- 技术栈、现有 CSS/样式方案、组件库、字体、图标和主题 token。
- 影响当前页面的组件、路由、状态和交互逻辑。

把**可直接观察到的问题**和**仍需验证的假设**分开。信息不全但可以合理推进时，说明你的假设；只有缺少会改变方案的关键需求时才追问。

### 2. 七个维度的诊断

逐项检查，与当前界面无关的维度可跳过。

| 维度 | 关键问题 | 方向 |
| --- | --- | --- |
| 信息层级 | 用户能否在 3 秒内认清主内容、主操作和次要工具？ | 明确优先级；内容聚焦，工具退后 |
| 空间与密度 | 留白有目的吗？分隔线是否过多？元素是挤还是散？ | 统一间距，减少切割，调整容器比例 |
| 字体与排版 | 字号、字重、行距有节奏吗？中文、拉丁字母和数字协调吗？ | 定义标题/正文/辅助层级；改善中文阅读 |
| 颜色与表面 | 所有东西是否都在同一平面？背景、面板、选中态是否可区分？ | 用少量表面层级，而不是到处加阴影 |
| 组件一致性 | 输入框、按钮、标签页、图标在尺寸和状态上是否一致？ | 收敛到共享 token 和组件变体 |
| 交互反馈 | 每个操作都有响应吗？空态和错误态完整吗？ | 补齐状态、无障碍、渐进披露 |
| 内容呈现 | 长文本、表格、公式、代码和图表是否匹配阅读任务？ | 按内容类型排版，而不是所有内容都用同一套默认样式 |

每个问题记录：**位置 → 可观察的证据 → 影响 → 最小改法 → 可以删掉什么**。

### 3. 按影响排序，只挑最重要的改动

优先级：
1. **P0 可用性**：文字难读、布局溢出、死交互、聚焦不可见、状态不完整。
2. **P1 结构与层级**：视觉权重不对、阅读宽度不合适、工具面板抢空间、控件重复。
3. **P2 一致性**：尺寸、间距、圆角、边框、颜色、图标和按钮状态不一致。
4. **P3 装饰细节**：微弱阴影、局部过渡和细微动效。

第一轮最多聚焦 **3 项高影响改动**。如果有更大的改造计划，拆到后续迭代；不要把许多互不相关的改动混进一次打磨。

### 4. 建立最小视觉规则

**从项目现有的 token 出发。** 只补缺失的部分；下面的基线不是强制风格：

- **间距**：使用 4 的少量倍数（4/8/12/16/24/32）；由组件语义决定用哪一档，而不是机械套阶梯。
- **圆角**：2–3 档就够。同一行、同一层级的控件共用一个圆角。
- **表面**：区分页面、内容、悬停/选中表面；边框必须用来分组或表达状态。
- **文字**：主、次、弱三级通常就够；不要把重要信息放进很浅的小字里。
- **强调色**：只用于主操作、选中和有意义的状态；不要为了"更丰富"给无关元素上色。
- **阴影**：只用于浮层、弹层和真实的高度关系；它替代不了清晰的布局。
- **动效**：短、自然、服务于反馈；尊重 reduced-motion；避免无意义的循环动画。

中文界面的额外检查：
- 优先选择在目标平台上渲染良好的中文字体回退；避免拉丁字体好看、中文却显得突兀的搭配。
- 阅读性文字要保证舒适的行宽和行距；工具型文字保持紧凑清晰。
- 检查中英数字和标点混排时的断行、挤压和基线错位。
- 公式、代码和表格按语义排版；不要用灰底盒子冒充"专业感"。

### 5. 动手修改（仅实现模式）

按这个顺序：
1. **删除**：重复入口、无用文案、过多分隔线、没有价值的状态标签、纯装饰容器。
2. **布局**：调整主次区域宽度、边距、内容最大宽度、对齐、密度和响应式行为。
3. **排版**：修正字号、行距、字重、文字颜色和长内容的阅读体验。
4. **组件**：用现有 token 统一按钮、输入框、标签页、面板、选中与聚焦状态。
5. **反馈**：补齐空/加载/错误/禁用/键盘状态，然后只加必要的动效。

实现约束：
- 尊重现有组件 API、路由、业务逻辑、数据流和状态管理。
- 不要为了视觉打磨重写业务架构；不要无理由地加依赖、设置项或新的可配置主题。
- 改共享 token 和少数关键组件，而不是到处覆盖样式。
- 每条新样式都要有明确目的；避免魔法数字和冗长的 CSS 覆盖链。
- 如果某个控件暴露了尚未接上的功能，不要用视觉把它藏起来；要么接上，要么明确标注不可用。

### 6. 验证与迭代

有运行/截图工具时，在相同页面、相同窗口尺寸、相同数据状态下前后对比：
- 视觉焦点是否更清楚？无意义的噪音是否减少？
- 中文标题、正文、代码和公式是否清晰，没有溢出、截断或跳动？
- 主操作、次操作、禁用、悬停、选中和键盘聚焦状态是否可区分？
- 窗口变窄、缩放变化或出现长文件名/长文本时是否仍然可用？
- 空、错误和加载状态是否保持布局稳定？
- 现有功能、导航、快捷键和数据关系是否完好？
- 文字和控件对比度是否达到项目的无障碍目标（正文 WCAG AA 4.5:1）？

运行项目已有的、与改动相关的 lint、类型检查、测试或构建命令。跑不了就如实说明；**不要声称"已验证"**。

如果结果只是"更好看"，而没有改善层级、阅读或操作，就回退。

### 新建模式

没有现成 UI 时，用下面的顺序替代步骤 1–5：

1. **定义工作。** 用一句话写清主要用户、主要任务和唯一最重要的操作。如果用户说不清，先给一版一句话草案请其修正。
2. **选屏幕形态。** 一个主屏，最多加一个次屏。列出 v1 的 3 个核心功能，其余明确搁置。
3. **定最小系统。** 定义 3–5 档间距、2–3 档圆角、3 级文字、一个强调色，以及页面/内容表面。从平台默认值起步；项目本来就在用 UI 库时才引入 UI 库。
4. **做完整的一条链路。** 端到端实现主要任务，包括空、加载、错误、禁用和窄屏状态。核心任务跑通之前，不加设置、主题或引导。
5. **验证。** 对新界面执行步骤 6。如果任务离开解释就走不通，先砍功能，再加 UI。

## 输出格式

### 评审模式

结构化、简短：

1. **总体判断**：一句话点出核心问题；不要用"缺乏高级感"这类空话。
2. **主要问题**：最多 3–5 条；每条包含位置、证据和影响。
3. **建议改动**：按优先级给出可执行步骤，并明确**该删掉什么**。
4. **第一轮任务**：最多 3 条，每条写明预期改善和验证方式。
5. **不确定项**：没有截图、代码或运行证据支撑的判断。

### 实现模式

汇报：

- **发现**：关键 UI 问题及其证据。
- **改动**：涉及的文件和改动点，尤其是删掉了什么。
- **验证**：跑过的命令、看过的页面、覆盖的状态和结果。
- **遗留问题**：未解决或无法验证的部分。

实现模式不要停在设计建议上：把改动做出来。除非改动可以被检查，否则不要说结果"更精致了"。

### 新建模式

汇报：

- **任务**：用一句话说明主要用户、任务和主要操作。
- **范围**：3 个核心功能，以及明确搁置了什么。
- **屏幕**：主屏和可能有的次屏。
- **系统**：间距、字体、圆角和颜色的决策，以及为什么适合这个产品。
- **验证**：检查过的屏幕和状态，以及哪些无法验证。

## 示例

### 评审模式：数据表格页

**总体判断**：表格本身可读，但筛选侧栏、表格和指标条都用了同一种白色表面，视线找不到入口。

**主要问题**
1. **筛选侧栏（左侧 280 px）**：表面和边框与表格相同，跟主内容抢注意力。把筛选收进表格上方的紧凑工具栏，删掉侧栏容器。
2. **表格行（行高 56 px，字号 13 px）**：对数据工具来说密度太低，1280×800 下只放得下 12 行。改成 40 px 行高、14 px 字号，再在同样视口复查。
3. **空状态（"暂无数据"加一个禁用导出按钮）**：用户分不清是该等还是该操作。说明为什么为空，给出下一步操作，去掉禁用的导出按钮。

**第一轮**
1. 筛选收进工具栏——只剩一条清晰的内容列；在 1280 px 和 1024 px 下验证。
2. 收紧表格密度——可见 16–18 行；在同样视口验证。
3. 重写空状态——下一步一眼可见；在零行和加载失败两种情况下验证。

**不确定项**：截图中看不到悬停和键盘聚焦。

### 实现模式：设置页

**发现**：输入框有三种高度（32/36/40 px）、两种聚焦样式；主按钮和危险按钮形状、字重完全相同。

**改动**
- 共享 token 样式表：新增控件高度和圆角 token。
- 设置表单：所有输入框使用共享高度和统一聚焦环；删掉逐字段的边框覆盖。
- 危险按钮：改用危险变体；确认文案现在说明影响数量和后果。
- 删掉每一行之间的分隔线；改由间距完成分组。

```css
:root {
  --control-height: 36px;
  --radius-control: 8px;
}
```

**验证**：`pnpm lint`、`pnpm typecheck`、`pnpm test` 均通过。查看过 1280×800 和 390×844；检查了空、加载、错误、禁用、悬停和键盘聚焦状态。

**遗留**：头像上传仍无错误状态；允许的文件类型需要产品决策。

### 新建模式：小型内部工具

**任务**：运维工程师需要找到失败的任务、读它的错误并重试；主要操作是重试。

**范围**：任务列表、带错误的任务详情、重试确认。搁置：调度、筛选、批量操作、审计日志。

**屏幕**：一个列表页加详情面板；没有仪表盘，没有设置。

**系统**：4/8/16/24 间距，6/10 圆角，13/15/20 字号，一个蓝色强调色，浅灰页面上的白色内容表面。

**验证**：在 1280 px 和 390 px 下检查了列表、空、加载、错误和重试失败状态；重试未连接真实后端。

### 请求变体

- **明确**："评审这个设置页，告诉我为什么它像后台管理页。"
- **隐含**："我们的仪表盘看着没问题，但什么都不突出；能修一下层级吗？"
- **截图**："这是我们定价页的截图——让它显得更经过考虑。"
- **新建**："我们需要一个小工具来重试失败的任务；先设计第一屏。"
- **超出范围**："为我们的新产品设计标志和品牌配色。"不触发；这是产品 UI 技能，不是品牌设计。

## 反模式

- 为了"高级感"叠加毛玻璃、渐变、模糊、阴影、大圆角和毫无意义的动效。
- 每块区域都加边框或卡片，直到页面像个组件陈列馆。
- 阅读区和工具区一视同仁，导致每个面板的视觉权重都一样。
- 靠缩小字号、降低对比度来制造"轻盈感"。
- 为了"极简"藏掉必要信息，直到用户找不到功能。
- 把未完成的状态或按钮做得更好看，却没有验证它到底做什么。
- 仅凭一张截图就断言某个框架、字体或技术是根因；没有证据不要下结论。
- 未经要求就重做产品定位、导航结构，或引入一整套新设计系统。

## 局限

- 静态代码无法证明视觉质量、动效、溢出或对比度。没有截图或运行页面时，这些判断只能算假设。
- 截图看不到键盘聚焦、悬停、加载、错误、空态和响应式行为。列出你没能检查的部分。
- 最小规则是基线，不是设计系统。项目没有 token 时，从现有取值归纳一小套，而不是发明新系统。
- 本技能改善的是现有产品内部的品质。它替代不了用户研究、品牌策略或完整的无障碍审计，也修不好缺失的产品功能或定位。
- 一次打磨不等于重新设计，创建品牌配色也不在范围内。如果层级从根本上就是错的，提成独立的改造；沿用现有品牌色，而不是发明品牌识别。

## 排障

| 症状 | 可能原因 | 处理 |
| --- | --- | --- |
| 页面显得平，但加阴影和渐变更糟 | 层级和间距没起作用 | 先修优先级和留白；结构清晰后再加装饰 |
| 截图好看，真实数据一进来就崩 | 只检查了默认状态 | 测长名称、空列表、错误、禁用控件和窄宽度 |
| 对比度"目测差不多" | 没算比值 | 量实际前景色和背景色；正文目标 4.5:1，大字和 UI 边缘 3:1 |
| 每个组件的高度或圆角都略有不同 | 样式是局部的，没有 token 化 | 收敛到共享的控件高度、圆角和间距 token；删除局部覆盖 |
| 打磨后更好看，却不好用了 | 只改了装饰，层级、阅读或操作没变 | 回退装饰性改动；只保留绑定到具体问题的改动 |
| 项目跑不起来也截不了图 | 没有运行时证据 | 只评审代码层面的问题；把视觉和交互结论标为未验证，并给用户一份简短的手工检查清单 |
| 改进与现有品牌或设计系统冲突 | 品牌规则和品质规则指向不同方向 | 以品牌约束为准；在约束内修层级、间距和状态。若品牌规则本身造成可用性问题，给出证据并请对方做品牌层面的决策 |

## 成功标准

完成后，用户应当更容易认清主内容、理解操作之间的关系、连续阅读并完成任务；同类组件行为一致，空状态是真实的，界面更安静但没有丢信息。**克制是结果，不是目的；清晰和可用才是目的。**
